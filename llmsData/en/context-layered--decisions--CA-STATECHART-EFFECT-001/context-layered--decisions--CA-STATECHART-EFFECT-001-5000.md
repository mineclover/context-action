CA-STATECHART-EFFECT-001: Separate `@context-action/xstate` Adapter Boundary and Core Integration Philosophy

CA-STATECHART-EFFECT-001: Separate @context-action/xstate Adapter Boundary and Core Integration Philosophy Status: accepted for implementation; publication cohort unapproved Owner: Framework Core & Runtime Integration Related issue/spec: CA-STATECHART-EFFECT-001 (packages/xstate/docs/xstate-effect-integration.md, CA-ELEMENT-INTEROP-001, CA-SPEC-EVIDENCE-001) Context Integrations with XState v5, XState v6 (xstate@beta), Effect v4, and @xstate/effect cross both orchestration (ActionRegister, SyncActionPipeline) and state observation/transaction coordination (StateReader, TransactionCoordinatorPort). Placing those bridges inside @context-action/core and @context-action/store-core creates duplicate structural ports (because @context-action/core and @context-action/store-core cannot import each other), leaks async Fiber/Scope concepts into ./element's 0ms DOM transport layer, and introduces irreconcilable npm/pnpm peer dependency diamond conflicts between xstate@^5 and @xstate/effect (which requires xstate@^6.0.0-alpha). Options considered - Keep ports split inside @context-action/core/element and @context-action/store-core: Rejected because it duplicates 7+ structural interfaces, couples DOM transport to Effect scopes, and cannot bind @context-action/core's main ActionRegister and @context-action/store-core together. - Create two separate runtime packages (@context-action/xstate and @context-action/effect): Held as future split option if standalone non-statechart Effect adapters outgrow .'s shared actor/guard contracts; rejected for now to avoid double versioning overhead for @xstate/effect workflows. - Option 1 (Accepted): Single optional package @context-action/xstate with . and ./effect subpaths: Keeps @context-action/core and @context-action/store-core zero-dependency while unifying synchronous and async Action, Store, Statechart, Schema, and Effect contracts through structural ports. Decision Extract all XState v5/v6 and Effect v4 / @xstate/effect bridges into @context-action/xstate (packages/xstate/) with two subpath exports: - @context-action/xstate (.): bindActor, bindActorToActionRegister, bindActorToSyncPipeline (bindStatechartToSyncPipeline), bindActorEmissions, waitForActorSnapshot, createActorStateReader, createActorActionEmitter, and enqueueSyncCommand. - @context-action/xstate/effect (./effect): fromStandardSchema, registerStandardSchemaGuard, registerEffectGuard, registerEffectHandler, bindEffectActorToActionRegister, runInTransactionScope, and framework-neutral bindActionDispatchTransactions. Declare runtime dependencies strictly on @context-action/core and @context-action/store-core without pinning mutually exclusive xstate / @xstate/effect peer version trees. Key points:
• **Keep ports split inside `@context-action/core/element` and `@context-action/store-core`**: Rejected because it duplicates 7+ structural interfaces, couples DOM transport to Effect scopes, and cannot bind `@context-action/core`'s main `ActionRegister` and `@context-action/store-core` together.
• **Create two separate runtime packages (`@context-action/xstate` and `@context-action/effect`)**: Held as future split option if standalone non-statechart Effect adapters outgrow `.`'s shared actor/guard contracts; rejected for now to avoid double versioning overhead for `@xstate/effect` workflows.
• **Option 1 (Accepted): Single optional package `@context-action/xstate` with `.` and `./effect` subpaths**: Keeps `@context-action/core` and `@context-action/store-core` zero-dependency while unifying synchronous and async Action, Store, Statechart, Schema, and Effect contracts through structural ports.
• **`@context-action/xstate` (`.`)**: `bindActor`, `bindActorToActionRegister`, `bindActorToSyncPipeline` (`bindStatechartToSyncPipeline`), `bindActorEmissions`, `waitForActorSnapshot`, `createActorStateReader`, `createActorActionEmitter`, and `enqueueSyncCommand`.
• **`@context-action/xstate/effect` (`./effect`)**: `fromStandardSchema`, `registerStandardSchemaGuard`, `registerEffectGuard`, `registerEffectHandler`, `bindEffectActorToActionRegister`, `runInTransactionScope`, and framework-neutral `bindActionDispatchTransactions`.
